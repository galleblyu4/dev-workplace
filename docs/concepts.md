# 필수 개념 정리

## 이미지와 컨테이너
Docker 이미지(Image)는 애플리케이션 실행에 필요한 파일과 구성을 담은 템플릿이다. Dockerfile의 `FROM nginx:alpine`, `COPY ...`를 기반으로 `docker build`를 실행하면 커스텀 이미지가 만들어진다. 컨테이너(Container)는 그 이미지로 시작한 실행 인스턴스다. 이미지는 저장·배포 단위, 컨테이너는 실행·중지·삭제 대상이다. 같은 이미지로 2개의 컨테이너를 만들 수 있다. 컨테이너 안에서 파일을 수정해도 원본 이미지는 자동 갱신되지 않는다. 변경을 재현하려면 Dockerfile과 소스를 수정하고 재빌드한다.

## 네트워크 네임스페이스 및 포트 매핑
Linux 컨테이너는 기본적으로 별도의 네트워크 네임스페이스와 네트워크 인터페이스/주소 환경을 사용한다. Nginx가 컨테이너 안에서 80번 포트로 열려 있다고 해서 Windows의 80번 포트에 자동 연결되는 것은 아니다. `docker run -p 8081:80 ...`은 호스트 8081번 포트로 들어온 요청을 컨테이너의 80번 포트로 전달한다. `EXPOSE 80`은 메타데이터이며 실제 외부 포트 게시를 대체하지 않는다. 동일한 호스트 포트는 일반적으로 둘 이상의 서비스가 동시에 점유할 수 없다.

## 절대경로와 상대경로
절대경로는 기준 디렉터리에 상관없이 파일의 위치를 지정한다. 예: `C:\Users\사용자\dev-workplace\index.html` 또는 Linux의 `/workspace/index.html`. 상대경로는 현재 작업 디렉터리를 기준으로 한다. 예: 프로젝트 루트에서 `./index.html`과 `./logs/07-build.txt`. 과제 README는 어느 컴퓨터에서나 사용할 수 있도록 상대경로를 기본으로 작성하고, 실행 스크립트는 `$PSScriptRoot`에서 프로젝트 위치를 계산한다.

## rwx와 chmod
리눅스 권한은 소유자(user), 그룹(group), 기타(other) 순서로 3자리 숫자로 표현한다. 읽기(r)는 4, 쓰기(w)는 2, 실행(x)은 1이다. `chmod 644 file.txt`는 `rw-r--r--`, `chmod 755 script.sh`는 `rwxr-xr-x`를 뜻한다. 디렉터리에서 x는 통과/탐색, r은 항목 이름 읽기, w는 항목 생성·삭제와 관련된다(실제 변경은 디렉터리 권한의 조합과 추가 정책에 따름). Windows 파일시스템의 ACL과 Linux chmod는 같지 않으므로 실습은 Ubuntu 컨테이너의 Linux 파일시스템에서 실행한다.

## Bind Mount와 Volume
Bind Mount는 호스트 컴퓨터의 특정 경로를 컨테이너에 직접 연결한다. 코드 편집과 실시간 화면 반영에 유리하지만 경로·파일 권한 등 호스트 환경에 의존한다. Volume은 Docker가 관리하는 저장 영역으로, 컨테이너를 삭제한 뒤 새 컨테이너에 다시 붙여도 데이터가 남는지 검증하기 적합하다. 데이터 지속 보관에는 Volume을, 개발 중 소스 공유에는 Bind Mount를 우선 고려한다.

## Git과 GitHub
Git은 로컬에서 커밋 이력을 관리하는 버전관리 시스템이다. GitHub는 원격 저장소를 호스팅하여 백업, 공유, 코드 리뷰, 협업을 가능하게 하는 서비스다. `git remote -v`는 로컬 저장소와 원격 저장소의 연결을 확인한다.

## 컨테이너 종료/유지, attach와 exec
`docker run --rm ubuntu echo hello`는 명령이 끝나면 컨테이너도 종료하고 삭제한다. 반면 `docker run -d --name ... ubuntu sleep ...`는 백그라운드에서 유지된다. `docker exec`는 실행 중인 컨테이너에 새로운 프로세스를 시작한다. `docker attach`는 실행 중인 컨테이너의 주 프로세스 입출력에 연결한다. 둘은 다르며, attach에서 종료 신호를 주면 주 프로세스/컨테이너에 영향을 줄 수 있으므로 검증에는 exec를 이용했다.
